## High-Level Architecture

This is a Go SDK for the Portal Account and Admin APIs. The project follows a code-generation-first approach with multi-spec architecture where HTTP client code is generated from separate OpenAPI specifications.

### Core Architecture

The SDK has a layered, multi-spec architecture with two public packages:

#### Packages

1. **Account Package** (`account/`)
   - User-facing account API
   - JWT authentication and 2FA
   - Quota status and history
   - Profile, avatar, and settings management
   - API key management

2. **Admin Package** (`admin/`)
   - Admin quota API (plans, allowances, config, stats, reconcile, cleanup)
   - Extensible for future admin APIs (billing, user CRUD, etc.)
   - Service pattern for organized API access

#### Layered Architecture

1. **OpenAPI Specifications Layer** (`specs/`)
   - `specs/account.yaml` - User-facing account API specification
   - `specs/admin/quota.yaml` - Admin quota API specification
   - Source of truth for all generated client code

2. **Generated Client Layer**
   - `internal/client/client.gen.go` - Auto-generated account HTTP client
   - `internal/admin/client.gen.go` - Auto-generated admin HTTP client
   - Contains all HTTP request/response types and client methods
   - Generated by `oapi-codegen` from swagger specs
   - Do NOT edit directly - changes will be overwritten

3. **Public API Layer**
   - `account/account.go` - Main AccountAPI interface and Client implementation
   - `admin/admin.go` - AdminAPI interface and AdminClient implementation
   - Provides higher-level abstractions, error handling, and convenience methods

4. **Testing Layer**
   - `account_test.go` - Account API unit tests
   - `admin/admin_test.go` - Admin API unit tests (28 test cases covering all quota methods)
   - `internal/client/mocks/` - Generated mocks for generated client interfaces
   - `mocks/AccountAPI.go` - Generated mocks for AccountAPI interface

### Key Design Patterns

**Functional Options Pattern**
Used extensively for client configuration and method parameters:
```go
client := account.NewClient(
    account.WithJWT(token),
    account.WithEndpoint("https://api.example.com"),
    account.WithDisableFollowRedirect(),
)
```

**Host Override Pattern**
Used for testing with vhosts where you need to connect to an IP address but send a different hostname in the Host header:
```go
// Connect to a local test server but send the production hostname in the Host header
client := account.NewClient(
    account.WithHostOverride("account.pinner.xyz", "http://127.0.0.1:8080"),
)
```

**Builder Pattern for List Operations**
Used for operations that accept filters, sorting, and pagination:
```go
ops, err := client.ListOperations(ctx,
    account.WithFilters(filter...),
    account.WithSorts(sort...),
    account.WithPagination(pagination),
    account.WithSearch("query"),
)
```

**Polling Pattern**
Used for long-running operations:
```go
op, err := client.WaitForOperation(ctx, id,
    account.WithPollInterval(2*time.Second),
    account.WithPollTimeout(5*time.Minute),
    account.WithPollSettledStates(account.OperationStatusCompleted),
)
```

**Error Handling with Centralized Mapping**
- Custom error types (`ErrUnauthorized`, `ErrOperationTimeout`)
- Centralized `httpErrorMessages` map operation IDs to status code-specific error messages
- `handleResponse()` function provides consistent error handling across all methods

### Code Generation Workflow

**From a running service (Swagger Update Pattern)**

When Portal API services are running locally, fetch and update specs:
```bash
# Fetch specs from local services (with Host header spoofing for vhosts)
curl -H "Host: account.localhost:8080" http://localhost:8080/swagger.yaml -o specs/account.yaml
curl -H "Host: admin.localhost:8080" http://localhost:8080/swagger.yaml -o specs/admin/quota.yaml

# Or use the swagger-update skill
# (See .aider-desk/skills/swagger-update/SKILL.md for details)
```

**From manual specification updates**

1. Modify `specs/account.yaml` or `specs/admin/quota.yaml` to change API contracts
2. Run `go generate ./...` to regenerate both clients:
   - `internal/client/client.gen.go` from `specs/account.yaml`
   - `internal/admin/client.gen.go` from `specs/admin/quota.yaml`
3. Update `account.go` or `admin/admin.go` if needed to use new generated types/methods
4. Regenerate mocks with `mockery --config .mockery.yaml` if interfaces changed
5. Run tests to verify changes

**Code Generation Configs**
- `oai-codegen.yaml` - Account client code generation
- `oai-codegen-admin.yaml` - Admin client code generation
- `.mockery.yaml` - Mock generation for testing

### Important Notes

- **Never edit generated client files directly** (`internal/client/client.gen.go`, `internal/admin/client.gen.go`) - they are auto-generated
- The `account` and `admin` packages are the public APIs; `internal/client` and `internal/admin` packages are internal implementation details and cannot be accessed by external consumers
- All generated code has `// DO NOT EDIT` comments at the top
- The SDK uses JWT authentication via `Authorization: Bearer {token}` header
- Default API endpoint is `account.pinner.xyz` (configurable via `WithEndpoint`)
- The SDK supports 2FA (OTP) with a two-step login process
- **Host Override**: Use `WithHostOverride(host, target)` for testing with vhosts. This allows connecting to a specific IP address while sending a different hostname in the Host header, useful when you cannot modify local DNS configuration.
- **Multi-Spec Architecture**: Separate.swagger specs in `specs/` directory for account and admin APIs ensures clean separation and easier maintenance
- **Admin Quota Service**: Full admin quota API for managing plans, allowances, configuration, stats, and reconciliation (see `admin/admin_test.go` for examples)

### Operation Status Flow

Operations have these statuses:
- `pending` - Operation is queued
- `running` - Operation is in progress
- `completed` - Operation finished successfully
- `failed` - Operation failed
- `error` - Operation encountered an error

The `WaitForOperation` method polls until the operation reaches a "settled" state (completed, failed, or error by default).
