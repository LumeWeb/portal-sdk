## Common Commands

### Build and Code Generation
```bash
# Generate client code from OpenAPI spec (runs go:generate directive at top of account.go)
go generate ./...

# Build the module
go build ./...

# Run tests
go test ./...

# Run tests with coverage
go test -cover ./...

# Run tests with verbose output
go test -v ./...

# Run tests with race detector
go test -race ./...

# Run a specific test
go test -v -run TestLogin ./...

# Run tests with coverage profile (used in CI)
go test -v -race -coverprofile=coverage.out -covermode=atomic ./...
```

### Dependency Management
```bash
# Tidy dependencies
go mod tidy

# Download dependencies
go mod download

# Verify dependencies
go mod verify
```

### Mock Generation
The project uses mockery with a configuration file (`.mockery.yaml`) to generate mocks for testing:
```bash
# Regenerate all mocks using the configuration file
mockery
```

The `.mockery.yaml` configuration generates mocks for:
- `go.lumeweb.com/portal-sdk.AccountAPI` → `mocks/AccountAPI.go`
- `go.lumeweb.com/portal-sdk/internal/client.ClientWithResponsesInterface` → `internal/client/mocks/ClientWithResponsesInterface.go`

### Version Management (Knope)
The project uses Knope for release management and changelog generation:
```bash
# Prepare a release (updates changelog, bumps version, commits changes)
knope prepare-release

# Create a release (creates GitHub release, tags commit)
knope release

# Document a change (creates a change file for changelog)
knope document-change
```

## High-Level Architecture

This is a Go SDK for the Portal Account API. The project follows a code-generation-first approach where HTTP client code is generated from an OpenAPI specification.

### Core Architecture

The SDK has a layered architecture:

1. **OpenAPI Specification Layer** (`swagger.yaml`)
   - Defines the API contract with all endpoints, request/response models
   - Source of truth for the generated client code

2. **Generated Client Layer** (`internal/client/client.gen.go`)
   - Auto-generated by `oapi-codegen` from swagger.yaml
   - Contains all HTTP request/response types and client methods
   - Do NOT edit this file directly - changes will be overwritten
   - Package: `internal/client` (internal implementation, not accessible externally)

3. **Public API Layer** (`account.go`)
   - Main public interface `AccountAPI` that consumers use
   - `Client` struct implements `AccountAPI` using the generated client
   - Provides higher-level abstractions, error handling, and convenience methods
   - Package: `account` (module root)

4. **Testing Layer**
   - `account_test.go` - Unit tests using httptest for HTTP mocking
   - `internal/client/mocks/` - Generated mocks for the generated client interface
   - `mocks/AccountAPI.go` - Generated mocks for the public AccountAPI interface

### Key Design Patterns

**Functional Options Pattern**
Used extensively for client configuration and method parameters:
```go
client := account.NewClient(
    account.WithJWT(token),
    account.WithEndpoint("https://api.example.com"),
    account.WithDisableFollowRedirect(),
)
```

**Host Override Pattern**
Used for testing with vhosts where you need to connect to an IP address but send a different hostname in the Host header:
```go
// Connect to a local test server but send the production hostname in the Host header
client := account.NewClient(
    account.WithHostOverride("account.pinner.xyz", "http://127.0.0.1:8080"),
)
```

**Builder Pattern for List Operations**
Used for operations that accept filters, sorting, and pagination:
```go
ops, err := client.ListOperations(ctx,
    account.WithFilters(filter...),
    account.WithSorts(sort...),
    account.WithPagination(pagination),
    account.WithSearch("query"),
)
```

**Polling Pattern**
Used for long-running operations:
```go
op, err := client.WaitForOperation(ctx, id,
    account.WithPollInterval(2*time.Second),
    account.WithPollTimeout(5*time.Minute),
    account.WithPollSettledStates(account.OperationStatusCompleted),
)
```

**Error Handling with Centralized Mapping**
- Custom error types (`ErrUnauthorized`, `ErrOperationTimeout`)
- Centralized `httpErrorMessages` map operation IDs to status code-specific error messages
- `handleResponse()` function provides consistent error handling across all methods

### Code Generation Workflow

1. Modify `swagger.yaml` to change API contract
2. Run `go generate ./...` to regenerate `internal/client/client.gen.go`
3. Update `account.go` if needed to use new generated types/methods
4. Regenerate mocks with `mockery --config .mockery.yaml` if interfaces changed
5. Run tests to verify changes

### CI/CD

**GitHub Actions Workflow (`.github/workflows/go.yml`)**
- Triggers on push and pull requests to `develop` branch
- Runs `go mod download`, `go mod verify`, `go build`
- Runs tests with race detector and coverage: `go test -v -race -coverprofile=coverage.out -covermode=atomic ./...`
- Posts coverage percentage as a PR comment

**Release Workflow (`.github/workflows/release.yml`)**
- Manual workflow dispatch
- Uses Knope to prepare and create releases
- Requires PAT (Personal Access Token) with write permissions

### Important Notes

- **Never edit `internal/client/client.gen.go` directly** - it's auto-generated
- The `account` package is the public API; `internal/client` package is internal implementation detail and cannot be accessed by external consumers
- All generated code has `// DO NOT EDIT` comments at the top
- The SDK uses JWT authentication via `Authorization: Bearer {token}` header
- Default API endpoint is `account.pinner.xyz` (configurable via `WithEndpoint`)
- The SDK supports 2FA (OTP) with a two-step login process
- **Host Override**: Use `WithHostOverride(host, target)` for testing with vhosts. This allows connecting to a specific IP address while sending a different hostname in the Host header, useful when you cannot modify local DNS configuration.

### Operation Status Flow

Operations have these statuses:
- `pending` - Operation is queued
- `running` - Operation is in progress
- `completed` - Operation finished successfully
- `failed` - Operation failed
- `error` - Operation encountered an error

The `WaitForOperation` method polls until the operation reaches a "settled" state (completed, failed, or error by default).
